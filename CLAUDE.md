# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Repository: https://github.com/c0ffee0wl/blaude

## Overview

blaude is a bash script that runs Claude Code inside a bubblewrap (bwrap) sandbox for security isolation. It provides filesystem, namespace, and capability isolation while allowing Claude Code to function normally within constrained boundaries.

## Running and Testing

```bash
./blaude                         # Run with defaults
./blaude --debug                 # Show bwrap command before executing
./blaude --dry-run               # Show command without executing
./blaude --exec bash             # Run bash inside sandbox for debugging
./blaude -c                      # Continue conversation
./blaude -p "hello"              # Prompt mode
./blaude -m /path/to/dir         # Mount read-only
./blaude -m /path/to/dir:rw      # Mount read-write
./blaude --git                   # Mount git config; pass GH_TOKEN/GITHUB_TOKEN
./blaude --ssh                   # Mount SSH keys and forward agent
./blaude --remote-control        # Enable Claude Remote Control; /remote-control on demand
./blaude remote-control          # Run Remote Control server mode (subcommand forwarded as-is, no --dangerously-skip-permissions)
./blaude --no-network            # Disable network namespace
./blaude --tmp                   # Run isolated in /tmp (no workspace)
./blaude --chic                  # Run claudechic TUI instead of claude
./blaude --keep-env              # Keep entire host environment
./blaude --clear-tmp             # Isolated tmpfs for /tmp
./blaude fix-apparmor            # Install AppArmor profile (Ubuntu 24.04+)
```

## Key Architecture

The script builds a `bwrap` command with these isolation layers:

1. **Namespace isolation**: PID, IPC, UTS, user namespaces with hostname "blaude"; optional network namespace with `--no-network`
2. **Capability dropping**: All capabilities dropped via `--cap-drop ALL`
3. **Filesystem sandboxing**: System dirs read-only, working dir + config read-write, ephemeral caches
4. **Environment sanitization**: `--clearenv` with selective passthrough of LLM API keys and essential vars

## Non-Obvious Design Decisions

- **`--new-session` intentionally omitted** from bwrap args — required for MCP server signal propagation. PID namespace provides equivalent process isolation.
- **Host-only cache dir (`$HOME/.cache/blaude`, mode 700)**: blaude's own trusted state — `_cached_bool` booleans (`wsl`, `overlay`), `_mount_linked_packages` results (`pkgmount-*`), and the resolv.conf temp file — lives here, **not** in `/tmp`. By default `/tmp` is bind-mounted read-write into the sandbox (`--bind /tmp /tmp`), so a contained agent could overwrite predictable `/tmp/blaude-*` files; the `pkgmount-*` cache in particular is read back and its paths bind-mounted on the next launch, so a poisoned cache there could mount arbitrary host dirs into the next session (read host secrets) or create+rw-mount host files. `$HOME/.cache/blaude` is safe because the sandbox shadows `$HOME` with a tmpfs (`--tmpfs $HOME`) and never binds this path back — the agent can't reach it. Defense-in-depth: the `pkgmount-*` cache is also re-validated on read (each line must be a real package root — a directory containing `package.json`, outside `$HOME`). The resolv temp file additionally uses `mktemp` (unguessable, `O_EXCL`, no symlink-follow). The `/tmp/blaude-mnt-warned-$UID` "warned once" flag stays in `/tmp` intentionally (UX flag, not security-relevant; per-session reset on reboot is desirable).
- **Mandatory protected paths**: Inspired by [sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime). Two strategies: (1) existing files → `--ro-bind` from host (preserves content, blocks writes); (2) existing directories → `--overlay-src + --tmp-overlay` (content readable, writes ephemeral, zero host artifacts). When a protected child dir doesn't exist but its parent does (e.g., `.git/hooks/` missing but `.git/` exists), the parent is overlaid instead — preventing child creation without host stubs. Root-level dotfiles (`.bashrc` etc.) are only protected if they exist (no overlayable parent; low risk since uncommon in project dirs). `.git/*` paths only protected when `.git` is a directory (not a file as in git worktrees). Protected files: `.bashrc`, `.bash_profile`, `.bash_login`, `.zshrc`, `.zprofile`, `.zshenv`, `.zlogin`, `.profile`, `.gitconfig`, `.gitmodules`, `.ripgreprc`, `.mcp.json`, `.git/config` (the shell-startup set tracks the code-execution-risk files Claude Code 2.1.160 prompts on — `--dangerously-skip-permissions`, which blaude always passes, bypasses those prompts, so the bwrap `--ro-bind` is the sole guard). Protected directories: `.git/hooks/`, `.vscode/`, `.idea/` — each only when it already exists. **Known gap, accepted**: in a repo that doesn't ship `.vscode/`, the sandbox can create it and write `settings.json`, whose executable-path keys (`git.path`, `python.defaultInterpreterPath`, `npm.bin`) run on the host when the folder is opened (Workspace Trust doesn't help — the write lands in a folder the user already trusts). Shadowing the absent name with a `--tmpfs` would block it, but bwrap must materialize the mountpoint through the workspace bind, leaving an empty `.vscode`/`.idea` stub in *every* project blaude runs in; that's unavoidable while the workspace is a host bind rather than an overlay, and not worth it for an IDE-gated risk. `.claude/` is intentionally left writable so agents can modify skills, agents, and settings. Override with `--allow-protected-writes` (also bypasses `$HOME` workspace/mount rejection). **Symlink guard (`_protected_src_ok`)**: before binding, each protected source is canonicalized with `readlink -f` and skipped unless it resolves (after following every symlink in its path) to inside the workspace. Without this, a malicious in-tree symlink (`.gitconfig` → `~/.ssh/id_rsa`, `.vscode` → `~/.aws`) would make bwrap bind the *host target's* content into the sandbox, leaking host files that the sandbox is specifically designed to exclude. A symlink *at* the protected name is **skipped with a warning**, because it cannot be protected: bwrap has no way to avoid resolving a bind destination, so the ro-bind/overlay lands on the link's target while the link itself stays an ordinary dentry. Binding it anyway was actively harmful — it silently made the *target* write-discarding (a benign `packages/*/.vscode -> shared` lost real edits) while still leaving the name replaceable. **Residual risk, accepted**: the name stays replaceable. Closing that would mean refusing to launch, which breaks legitimate shared-config symlinks; there is no in-place alternative, since nothing can be mounted onto a symlink.
- **Nested protected-paths scan**: After applying the static top-level list, a `find -mindepth 2 -maxdepth 3` scan (`_scan_nested`) protects the same paths inside subdirs — covers monorepos and vendored deps (e.g. `packages/app/.git/hooks/`). `.git/.vscode/.idea` use `-prune` so we treat each as a unit. Both branches also match `-type l`: under find's default `-P` a symlink is neither `-type d` nor `-type f`, so a symlinked protected name would be invisible to the scan — it needs to reach `_protected_src_ok` to be skipped-with-warning rather than silently mis-mounted onto its target. The static list runs first as a fail-safe; the scan adds depth. **Submodules are not covered by this scan** — see the `.git/modules` note below.
- **Submodule gitdirs (`.git/modules/*`)**: A submodule's real gitdir lives at `.git/modules/<name>/`, arbitrarily nested (a submodule in a subdir, or a submodule of a submodule), so its `config`/`hooks/` sit well past the nested scan's `maxdepth` — and `<sub>/.git` is a gitlink *file* that `-d`/`-type d` never match. These execute on the host exactly like top-level ones: `core.fsmonitor` set in a submodule config fires on a plain `git status` in the **superproject**, since git recurses to compute submodule dirtiness. `_protect_git` therefore walks `.git/modules` by `HEAD` file and applies the same config+hooks strategy (`_protect_gitdir`) to each gitdir root. The `HEAD` walk is filtered by `[[ -d objects || -f config ]]` — `HEAD` also names the reflog (`logs/HEAD`) and a remote's default ref (`refs/remotes/*/HEAD`), and overlaying those would silently discard submodule reflog and fetch updates. Skipped when the whole gitdir was already overlaid (no `hooks/`), which covers it anyway.
- **Mount validation**: Mount targets (`-m`) are resolved via `readlink -f` — broken symlinks rejected, `$HOME` mounts blocked (unless `--allow-protected-writes`). Workspace rejected if it resolves to `$HOME` (unless `--allow-protected-writes`).
- **Workspace symlink pre-scan**: `_scan_workspace_symlinks` runs `find -maxdepth 4 -type l` and warns when a symlink resolves (via `readlink -m`) to anything outside the workspace AND outside known-safe system roots (`/usr`, `/lib*`, `/bin`, `/sbin`, `/etc`, `/proc`, `/sys`, `/dev`). Bwrap's mount namespace already prevents symlinks from resolving to unmounted host paths, but a `-m foo:rw` could combine with an in-tree symlink to expose an unintended host file — the warning lets the user notice. Skipped under `--allow-protected-writes`.
- **`exec` vs non-exec bwrap**: The default path calls `_blaude_cleanup` then `exec` (clean process tree, direct signal delivery). WSL2 needs post-bwrap `sync` and asciinema needs post-bwrap SIGCONT — both require blaude to stay alive, so they share a unified non-exec path with `_blaude_exit` trap function. The condition is `[[ "$wsl_mode" == true || -n "$_asciinema_pid" ]]`.
- **Sandbox bypass commands**: `update`, `install`, `install-github-app` exec claude directly (need write access outside sandbox). Checked both as `$1` and after flag parsing (e.g., `./blaude --debug install`). `fix-apparmor` also bypasses the sandbox (writes to `/etc/apparmor.d/` via sudo).
- **Auto-configures `~/.claude/.claude.json`** with `hasCompletedOnboarding` and `bypassPermissionsModeAccepted` flags. Uses `jq` if available for merging; without `jq` it returns rather than overwriting. Updates both `$CLAUDE_CONFIG_DIR/.claude.json` and `~/.claude.json`. **Symlink hardening**: this runs on the host, pre-sandbox, with full user privileges, but `$config_dir` is bind-mounted read-write into the sandbox as a *directory* — only `$HOME/.claude.json` is pinned as a file bind, so a contained agent can unlink `$config_dir/.claude.json` and plant symlinks beside it. Shell redirects follow those, which turned this into an arbitrary host-file write. Two guards: (1) a symlink at `$file` is refused (`! -f` is *true* for a dangling one, so the `echo >` would otherwise create the link's target); (2) the merge writes to `mktemp` (O_EXCL, unguessable, no symlink follow) instead of the predictable `${file}.tmp`, whose name a pre-planted symlink could use to redirect jq's output — which embeds agent-controlled JSON verbatim. The final `mv` is a rename, not a write-through, and `$file` is known not to be a symlink by then. `_mount_linked_packages`' token-file `: >` writes share the same exposure and rely on being created before the sandbox starts.
- **Bypass-permissions blocker detection** (`_warn_if_bypass_disabled`): scans `$config_dir/settings.json`, `~/.claude/settings.json`, `/etc/claude-code/managed-settings.json`, any `/etc/claude-code/managed-settings.d/*.json` (drop-in fragments, Claude Code 2.1.83+), and the workspace's own `.claude/settings.json` / `.claude/settings.local.json` (the key is documented as working from any scope, so a repo can disable bypass mode too; read from `$current_dir` — `$workspace` is the in-sandbox path and isn't assigned until much later — and skipped under `--tmp`, where the workspace is never mounted) for `permissions.disableBypassPermissionsMode: "disable"`. If found, prints a warning at startup — that key blocks `--dangerously-skip-permissions` (which blaude always passes), and we cannot override managed (enterprise) settings. The "managed" warning fires for any path under `/etc/claude-code/`. **Important**: the regex check uses `$(< file)` *without* `2>/dev/null`; combining the bash file-read optimization with a redirect silently returns empty (subshell becomes a no-op). Existence + readability checks are sufficient before the read.
- **`DISABLE_UPDATES` (Claude Code 2.1.118+, stricter than `DISABLE_AUTOUPDATER` which blaude already hardcodes)**: passed through in the `Updates & Installation` block. The sandbox-bypass commands `update`/`install`/`install-github-app` exec claude directly with the inherited host env, so claude's own enforcement fires (prints "Updates are disabled by your administrator. Contact your IT team to get the latest version."). No blaude-side guard needed — duplicating it would just diverge from claude's message.
- **Remote Control (`--remote-control` flag / `remote-control` subcommand)**: Claude Code's [Remote Control](https://code.claude.com/docs/en/remote-control) (drive a local session from phone/browser) checks eligibility through the **GrowthBook feature-flag service**. blaude's default telemetry opt-outs kill that layer, so RC fails with the misleading "Remote Control is not yet enabled for your account" error (confirmed upstream: setting `DISABLE_TELEMETRY=1`/`DO_NOT_TRACK=1` flips claude into "no-telemetry" mode which disables GrowthBook entirely; `DISABLE_GROWTHBOOK=1` stops the fetch directly). **`remote_control_mode`** is set by two triggers: the consumed `--remote-control` flag (env-prepped but **not** forwarded — claude starts a normal `--dangerously-skip-permissions` session and the user runs `/remote-control` on demand) and the bare `remote-control` subcommand in `command_args[0]` (server mode; matched only in position 0 to avoid false positives like `-p "remote-control"`). The subcommand is forwarded **verbatim without `--dangerously-skip-permissions`** — claude's `remote-control` subcommand must be the first token and rejects that flag (`Error: Unknown argument: remote-control` otherwise), and Remote Control enforces permission prompts regardless; this needs a dedicated branch in the `Build command` section since blaude otherwise prepends the flag to every invocation. In this mode blaude (a) omits `DO_NOT_TRACK`/`DISABLE_TELEMETRY`/`DISABLE_GROWTHBOOK` from `_hardcoded_env_vars` and force-unsets them, and (b) force-unsets the auth vars `ANTHROPIC_API_KEY`/`CLAUDE_CODE_OAUTH_TOKEN` (RC needs a full-scope claude.ai OAuth session — a host API key or limited-scope token blocks it), warning when either was present. Two inherent Claude Code caveats (not fixable here, documented in the startup notice): enabling RC necessarily lets telemetry/feature-flag traffic flow (no RC without telemetry), and RC re-enables permission prompts for remote-driven actions despite `--dangerously-skip-permissions`. `CLAUDE_CLIENT_PRESENCE_FILE` (screen-lock push suppression) is already bound read-only; `remote-control` is **not** a sandbox-bypass command (it runs sandboxed).
- **Write-discarding overlays for host state (`_overlay_or_bind`)**: The rule is *host state the agent should read but never durably change gets an overlay; host state that **is** the agent's output stays read-write*. Overlaid: `~/.config`, `~/.npm`, `~/.cache/uv`, `~/.bun/install/cache`. Still read-write: the workspace and `~/.claude` (sessions, `history.jsonl`, project trust and `-c`/`--resume` all have to persist — deliberate, and it leaves `~/.claude/settings.json`, the `statusLine.command` target and `plugins/` as an accepted deferred-execution surface). The motivating case is `~/.config`: it holds `autostart/`, `systemd/user/`, `environment.d/`, `Code/User/settings.json` and `nvim/init.lua`, each of which executes on the *host* at next login or next app launch, and because blaude always passes `--dangerously-skip-permissions` the Claude Code 2.1.160 write prompts never fire — bwrap is the only guard. Plain read-only was rejected because it breaks documented use: Chrome cannot start against a read-only profile (`~/.config/google-chrome` is the profile, not the cache) and yarn globals live in `~/.config/yarn`. An overlay also beats a denylist of dangerous subdirs, which would need maintaining forever. The caches are a weaker case (poisoning `_cacache`/uv only feeds tampered install scripts to the host's *own* later `npm`/`uv` runs) but cost nothing to include. Two caveats: the upper layer is tmpfs, i.e. **RAM** — a heavy `npm ci` or `uv pip install torch` writes gigabytes into memory — and uv's default `link-mode=hardlink` can't hardlink across the overlay into a workspace venv, so it degrades to copying. `--allow-protected-writes` restores plain read-write binds throughout. When bwrap predates 0.8.0 the helper falls back to today's behaviour and warns once naming the paths; `~/.bun/install/cache` falls back to `--tmpfs` rather than a bind, since a bind would *newly* expose a directory that is blank today. Note this only covers the capability gap — if overlayfs is supported but refuses to mount on the underlying filesystem (some WSL2 drvfs or NFS homes) bwrap still aborts, exactly as the pre-existing `.git/hooks` overlay does.
- **`/tmp` IPC socket shadows (partial mitigation, `--clear-tmp` is the complete one)**: `--bind /tmp /tmp` (the default) also exposes `/tmp`'s IPC endpoints, reachable because the sandbox runs as the uid that owns them. The sharpest is a live tmux server: `/tmp/tmux-$UID/default` + `tmux send-keys` types into a host shell, which is *immediate* host code execution, not the deferred kind everything else here guards against. An ssh-agent socket at `/tmp/ssh-XXXX/` is an opt-out bypass of the `--ssh` gate, and `/tmp/dbus-*` bypasses `--keyring` the same way. blaude shadows each with an empty `--tmpfs`: fixed names `.X11-unix`, `.ICE-unix`, `.XIM-unix`, `.font-unix` plus `tmux-*`, `ssh-*`, `dbus-*` globs, **only when the directory already exists** — `--tmpfs` on a missing path makes bwrap materialize the mountpoint, which under a host-bound `/tmp` creates a real host directory. Skipped under `--clear-tmp` (already a private tmpfs) and `--allow-protected-writes`. **Two accepted gaps**: bare socket *files* at the `/tmp` root (`/tmp/.s.PGSQL.5432`, `/tmp/mysql.sock`) can't be shadowed by a tmpfs without covering `/tmp` itself, and a tmux server started *after* launch creates its socket dir mid-session, unshadowed. `--clear-tmp` closes both.
- **Cross-session messaging reaches the host (known gap, documented not closed)**: Claude Code 2.1.224 added cross-session `SendMessage`/`ListAgents` — every session registers itself at `~/.claude/sessions/<pid>.json` and binds an inbox socket under `$TMPDIR`. The docs state that "a container has its own filesystem, so a session inside it and a session on the host can't reach each other", but **that does not hold for blaude**: `~/.claude` is bind-mounted read-write and `/tmp` is bind-mounted read-write by default, so the sandboxed session and the user's host sessions share both halves of the channel and can discover and message each other. The direction that matters is outbound — a contained agent can message an *unsandboxed* host session. The blast radius is bounded by Claude Code's own hardening (2.1.152+: relayed messages carry no user authority, receivers refuse relayed permission requests, `/`-commands in message text arrive as plain text and are never executed, and the receiving session's own permission rules still apply), so this is a prompt-injection channel rather than a code-execution one. Inbound is covered by `crossSessionInbound` (2.1.225), which holds peer messages for approval in exactly the bypass-permissions sessions blaude always creates. Closing the outbound path would mean shadowing `~/.claude/sessions` with a tmpfs — deliberately not done, since it also breaks the legitimate case of several blaude sessions coordinating. Users who want the channel shut can run `--clear-tmp` (isolates the socket dir) or deny the `SendMessage` tool in settings. `CLAUDE_CODE_MESSAGING_SOCKET` is separately force-unset (see the Environment Variable Passthrough section) so an *inherited* host socket path isn't handed to sandboxed hooks.
- **UID mapping**: Root users get mapped to UID 1000 inside sandbox; non-root keeps their UID. Required for `--dangerously-skip-permissions`.
- **D-Bus/keytar disabled by default** — file-based token storage is more reliable in headless environments (WSL2, containers). Use `--keyring` only if GNOME Keyring is properly configured and unlocked.
- **`/run/user/$UID` is tmpfs, not `--dir`** — explicit empty RAM-disk blocks accidental host re-binds under XDG runtime dir. `XDG_RUNTIME_DIR=/run/user/$sandbox_uid` is set unconditionally so apps don't fall back to `/tmp` or warn. Wayland/PipeWire/D-Bus sockets only land in the sandbox via opt-in: `--keyring` re-binds the host's D-Bus session socket on top of the tmpfs after the fact (later `bwrap_args` entries override the tmpfs at the bind path).
- **`--git` mounts the GPG agent socket dir** via `gpgconf --list-dirs socketdir` (canonical XDG-aware lookup, handles `XDG_RUNTIME_DIR/gnupg` vs `~/.gnupg` vs custom `GNUPGHOME` transparently). Needed for `commit.gpgsign=true`. `GPG_TTY` and `GNUPGHOME` are auto-passed when set, and the `GNUPGHOME` directory itself is read-only-bind-mounted via `_bind_env_path` (custom keyring location must exist inside the sandbox). Decoupled from `--ssh` because GPG-signed commits work without SSH (e.g. with `gh` over HTTPS).
- **`--ssh` binds the socket's parent dir**, not just `$SSH_AUTH_SOCK` itself. `systemctl --user restart ssh-agent` recreates the socket file under the same dir, so binding the parent keeps the connection alive across rotations. Path computed as `${SSH_AUTH_SOCK%/*}` to avoid a `dirname` fork.
- **Asciinema pause/resume**: When `ASCIINEMA_REC=1`, blaude finds the asciinema process by walking `/proc` ancestors and sends SIGSTOP before sandbox execution and SIGCONT on exit (via EXIT trap). This pauses recording during the Claude session. When asciinema is paused, blaude cannot `exec` into bwrap (needs to stay alive for the SIGCONT trap), so it runs bwrap as a child process — same pattern as the WSL2 path.
- **`osc52-clipboard` companion**: VTE terminals (Terminator, GNOME Terminal) don't support OSC 52 clipboard. `osc52-clipboard` is a Python 3 PTY proxy (stdlib only, requires 3.9+) that intercepts OSC 52 sequences via a state machine and copies to clipboard via xclip/xsel/wl-copy. Auto-detected from same directory as blaude, then PATH. **Always activated when available** — provides clipboard support regardless of NO_FLICKER mode. Runs outside the sandbox (wraps bwrap) so it has access to DISPLAY/WAYLAND_DISPLAY. Uses `pty.fork()` with a custom I/O loop that handles stdin relay, raw mode, and SIGWINCH propagation. Clipboard writes have a 3-second timeout to prevent terminal freeze on broken X11/Wayland. Disable with `--no-clipboard` or `OSC52_NO_CLIPBOARD=1`.
- **Linked package auto-detection** (`_mount_linked_packages`): Shared helper used by nvm, bun, fnm, and pnpm. Scans for symlinks pointing outside the package manager directory, resolves to package root (directory with `package.json`), mounts read-only. Safety: never mounts `$HOME` itself. nvm scans `~/.nvm/versions/*/node_modules/`; bun scans `~/.bun/bin/` and `~/.bun/install/global/node_modules/` (avoids traversing `~/.bun/install/cache/`); fnm scans `$FNM_DIR/node-versions/`; pnpm scans only `$PNPM_HOME/global/` (deliberately **not** the content store under `$PNPM_HOME/store` — it holds tens of thousands of internal symlinks that all resolve within `$PNPM_HOME`, so scanning it is pure cost; `pnpm link --global`/`pnpm add -g <local dir>` symlinks that escape live under `global/`).
- **MCP token files mounted read-write** over read-only package mounts — token files (`.token-cache.json`, `.selected-account.json`) live at package root, not `$HOME`.
- **`/opt` front-end symlink resolution**: `/opt` is built as an *empty* `--dir` with only blaude's own shim subdirs (`host-bin`/`host-cargo-bin`/`host-go-bin`) mounted into it — the host `/opt` is never exposed. But many FHS "add-on" packages drop a launcher in `/usr/bin` that is a symlink into `/opt` (e.g. `pwsh` → `/opt/microsoft/powershell/7/pwsh`; `google-chrome-stable` → `/opt/google/chrome/google-chrome`, often via an `/etc/alternatives` hop). `/usr/bin` is on the sandbox PATH (and `/etc` is ro-bound, so the alternatives hop resolves), but the empty `/opt` shadows the final target, so the symlink dangles and the tool reports "not available" in-sandbox. Fix: a guarded loop iterates a small list of dev-relevant tool names (`pwsh`/`pwsh-preview`, `google-chrome*`, `chromium*`, `microsoft-edge*`, `brave-browser`, `dotnet`), runs `readlink -f "$(command -v <tool>)"` (follows the whole chain), and **only** when the resolved path is under `/opt/*` ro-binds its install dir (the binary's parent). A `_opt_seen` associative array dedups shared dirs (e.g. `google-chrome` + `google-chrome-stable` → same `/opt/google/chrome`). The `/opt/*` guard is what makes the list safe regardless of install method: a tool that is a real `/usr/bin` file or a snap (`/snap/…`) resolves elsewhere and is skipped. Read-only, only-if-present. Caveat (documented for browser-automation MCP users): Chrome/Chromium's own setuid sandbox can't run under bwrap's dropped caps, so they must be launched with `--no-sandbox` inside blaude. Snap-packaged browsers aren't supported (snap needs loopback-mount machinery bwrap can't provide).
- **fnm (Fast Node Manager) support**: fnm exposes the active Node version through a *per-shell* symlink `$FNM_MULTISHELL_PATH = $XDG_RUNTIME_DIR/fnm_multishells/<pid>_<ts>` → `$FNM_DIR/aliases/default` → `$FNM_DIR/node-versions/<v>/installation`, and prepends `$FNM_MULTISHELL_PATH/bin` to PATH (that's why `which node` shows a `/run/user/...` path). Inside the sandbox `$XDG_RUNTIME_DIR` is an empty tmpfs and `$FNM_DIR` (default `~/.local/share/fnm`, NOT under the mounted `~/.local/share/claude`) is gone, so node/npm/npx vanish. Fix mirrors the nvm block: ro-bind `$FNM_DIR`, then **`readlink -f` the active bin dir down to its canonical `node-versions/<v>/installation/bin`** under `$FNM_DIR` — never bind the ephemeral `/run/user/.../fnm_multishells` path, which won't exist in-sandbox. Selection priority: `$FNM_MULTISHELL_PATH` (active in the launching shell) → `$FNM_DIR/aliases/default` → newest install; a `== "$fnm_dir"/*` guard ensures only a mounted path is added to PATH. **PATH ordering**: the bin of whichever Node manager is *active in the launching shell* (fnm via `FNM_MULTISHELL_PATH`, nvm via `NVM_BIN`; fnm wins if both) is **prepended to the front of PATH** — mirroring how fnm/nvm prepend on the host — so `node`/`npm`/`npx` resolve to the user's selected version instead of being shadowed by an earlier entry (notably `~/.bun/bin`, which often ships a `node` shim, or a system node). A manager that is merely *installed but not active* in this shell is appended as a low-priority fallback instead, so it can't override the user's actual node (this also applies to nvm, fixing the same latent shadowing). `fnm env` always exports `FNM_DIR`, so custom/`XDG_DATA_HOME` locations are honored. The `$FNM_DIR/fnm` binary (curl install) is added to PATH so `fnm ls`/`fnm use <installed>` work; `fnm install` doesn't (ro mount). `FNM_DIR` is re-`--setenv` to the mounted path; like nvm, `NPM_CONFIG_PREFIX` is skipped (fnm manages its own prefix inside the install).
- **Secondary Node package managers (pnpm/corepack/yarn)** are mounted **tool-agnostically** (gated on dir existence, not on fnm) because their global installs, bin shims, and caches live OUTSIDE any node-manager dir and are wiped by the `--tmpfs $HOME` shadow — so this also fixes nvm/bun setups. pnpm: ro-bind `$PNPM_HOME` (covers `bin/`, `global/`, `store/`), add `$PNPM_HOME/bin` to PATH, `--setenv PNPM_HOME`. corepack: ro-bind `$COREPACK_HOME` (`~/.cache/node/corepack`; holds `v1/{npm,yarn,pnpm}/<version>/` + `lastKnownGood.json`) so corepack-pinned pnpm/yarn resolve offline — the shims themselves are in node's bin dir, already mounted — `--setenv COREPACK_HOME`. yarn classic: ro-bind `~/.yarn`, add `~/.yarn/bin` to PATH (yarn globals live in the rw `~/.config/yarn`). All read-only, so running installed tools works but `-g` installs / `pnpm dlx` / `corepack` downloads of *uncached* versions don't persist — consistent with the existing nvm/bun behavior.
- **claudechic config**: Do NOT bind-mount `~/.claude/.claudechic.yaml` directly — claudechic uses atomic writes (`os.replace`) which fail on bind-mounted files. It's already accessible via the `~/.claude` mount.
- **CLAUDE_CODE_TMPDIR**: If set to something other than `/tmp`, a tmpfs is created at that path inside the sandbox.

## WSL2/systemd resolv.conf Handling

This is a tricky two-phase workaround for bwrap following symlinks:

- If `/etc/resolv.conf` → `/run/systemd/resolve/stub-resolv.conf`, bwrap tries to create the file at the symlink target, but `/run` doesn't exist yet when `/etc` is mounted.
- **Solution**: Save symlink target and content early, then after `--tmpfs /run` is added, create the target directory and mount resolv.conf content there.
- Reference: https://github.com/containers/bubblewrap/issues/390

## Environment Variable Passthrough

**Prefix passthrough**: every host env var starting with `ANTHROPIC_` or `CLAUDE_` is auto-passed via the env scanning loop, and the per-model families `VERTEX_REGION_*` / `DISABLE_PROMPT_CACHING*` are glob-matched there too. These namespaces are owned, so new upstream env vars (e.g. anything added for future Claude Code releases or models) require no blaude change. The explicit `claude_env_vars` array covers only non-prefix passthrough — third-party LLM keys, cloud auth (AWS/GCP/Azure), OpenTelemetry/MCP standards, and a handful of bare names (`CLAUDECODE`, `AI_AGENT`, `DEBUG`, `IS_DEMO`, `CCR_FORCE_BUNDLE`, etc.).

- **Hardcoded vars** (set unconditionally via `--setenv`, also under `--keep-env`, override host values): `DISABLE_AUTOUPDATER=1`, `DISABLE_ERROR_REPORTING=1`, `DISABLE_BUG_COMMAND=1`, `CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY=1`, `DISABLE_INSTALL_GITHUB_APP_COMMAND=1`, `CLAUDE_DISABLE_CONFIG_WATCH=1`. Plus the telemetry/feature-flag opt-outs `DO_NOT_TRACK=1`, `DISABLE_TELEMETRY=1`, `DISABLE_GROWTHBOOK=1` — appended **only when not in Remote Control mode** (see the Remote Control entry under Non-Obvious Design Decisions; in RC mode they are force-unset instead). Stored as `KEY=VALUE` pairs in `_hardcoded_env_vars`. Enforced via a deny-set in the passthrough loop so the prefix match cannot accidentally re-pass them. Never add these to passthrough.
- **Hardcoded unsets** (forced absent via `--unsetenv`, also under `--keep-env`): stored in `_hardcoded_unsetenv_vars`, all included in the loop deny-set so the `ANTHROPIC_*`/`CLAUDE_*` prefix match cannot resurrect them. In **Remote Control mode** this list gains `DO_NOT_TRACK`, `DISABLE_TELEMETRY`, `DISABLE_GROWTHBOOK` (so the GrowthBook eligibility check can run) and the auth vars `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` (RC requires a full-scope claude.ai OAuth session; a host API key or limited-scope token triggers the misleading "not yet enabled" error). Adding them to the deny-set is what blocks the prefix match from re-passing the two auth vars.
  - `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` — the upstream hardening predicate fires whenever the variable is *defined* (it overrides `--dangerously-skip-permissions`, symptom: `Permission mode forced to default — CLAUDE_CODE_SUBPROCESS_ENV_SCRUB is set …`), and `=0` does not suppress the banner despite the advice embedded in it. blaude matches the documented default of "unset = disabled" instead of zeroing.
  - `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_BRIDGE_SESSION_ID`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_TEAM_NAME`, `CLAUDE_CODE_REMOTE`, `CLAUDE_CODE_REMOTE_SESSION_ID`, `CLAUDE_EFFORT`, `CLAUDE_PROJECT_DIR`, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_PID` — outer-claude auto-set markers (parent's binary identity, parent's session UUID, parent's Remote Control session ID (2.1.199+), nested-session flag (2.1.172+), parent's agent-team membership, parent's claude.ai cloud-session identity, parent turn's effort level, parent's project cwd, parent's cross-session inbox socket (2.1.224), parent's PID (2.1.214)). Pre-prefix-passthrough, these were never in the explicit whitelist so they were silently filtered. The prefix match would inherit them into the sandboxed inner claude on nested invocations — wrong identity, wrong paths (outer binary unreachable inside the sandbox), conflated session telemetry. `CLAUDE_CODE_CHILD_SESSION=1` is the concretely harmful one: an inherited value excludes the sandboxed session from `--resume`/`--continue`/up-arrow history, silently breaking `blaude -c`. Force-unset so inner claude starts with clean identity. The last two are documented as "set by Claude Code, not by you" and are re-exported by the inner claude for its own subprocesses, so unsetting them is mostly hygiene — with two exceptions: `CLAUDE_CODE_MESSAGING_SOCKET`'s value stays *live* across the boundary (the socket sits under the bind-mounted `/tmp`), handing sandboxed hooks and Bash commands a writable pointer into the **host** session's inbox, and `CLAUDE_PID` names an unrelated process once inside the PID namespace, where the Bash tool's `pkill` self-protection guard reads it.
- **GitHub tokens** (`GH_TOKEN`, `GITHUB_TOKEN`): Only passed with `--git` flag.
- **Glob patterns**: `ANTHROPIC_*`, `CLAUDE_*`, `VERTEX_REGION_*`, `DISABLE_PROMPT_CACHING*`, `WARP_*`, `MCP_SERVER_*`, `*_WEBHOOK`, and `WEBSHARE_*` are auto-passed via the env scanning loop. The two model-family globs replaced per-model enumeration (every new Claude model used to require a blaude commit). `CLAUDE_MEM_*` is covered by `CLAUDE_*`. `MCP_SERVER_*` covers the documented env-based MCP server-config format (`MCP_SERVER_<SERVER_ID>=<COMMAND>`) and subsumes the explicit `MCP_SERVER_CONNECTION_BATCH_SIZE`.
- **Terminal integration (`WARP_*`, `TERM_PROGRAM`)**: The [claude-code-warp](https://github.com/warpdotdev/claude-code-warp) extension (and forks like [zap](https://github.com/zerx-lab/zap)) deliver notifications via OSC 777 escape sequences over the TTY. Its hook scripts only emit when the terminal is detected: `should-use-structured.sh` requires `WARP_CLI_AGENT_PROTOCOL_VERSION` + `WARP_CLIENT_VERSION` (structured path), and the legacy fallback in `on-notification.sh`/`on-stop.sh` requires `TERM_PROGRAM=WarpTerminal`. Warp/zap inject these into spawned shells, but `--clearenv` would strip them, silently disabling all notifications. `WARP_*` (glob) plus bare `TERM_PROGRAM`/`TERM_PROGRAM_VERSION` are passed through so the hooks fire. No socket/mount is needed — OSC 777 rides the existing stdout/`/dev/tty`, and the osc52-clipboard proxy passes non-`52;` OSC sequences through verbatim. (`jq` must be installed on the host — it's an extension prerequisite and is reachable inside the sandbox via the read-only `/usr` mount.)
- **Auto-mounted file/path vars**: Vars pointing to files/dirs need both passthrough AND a bind-mount. The prefix match handles passthrough; the bind-mount loop must still be updated when a new path-typed var is added upstream. Currently mounted: `CLAUDE_ENV_FILE`, `CLAUDE_CODE_PLUGIN_SEED_DIR`, `CLAUDE_CODE_PLUGIN_CACHE_DIR`, `CLAUDE_PLUGIN_DATA`, `CLAUDE_SKILL_DIR`, `CLAUDE_CODE_WORKSPACE_DIR`, `CLAUDE_LOGS_DIR`, `CLAUDE_MCP_STDERR_LOG_DIR`, `CLAUDE_SESSION_METADATA_DIR`, `CLAUDE_CODE_WORKSPACE_STATE_DIR` (the four `*_DIR` overrides all default under the already-mounted `~/.claude`; bound read-write only when pointed at a custom host path that exists, matching the other claude-managed dirs), `CLAUDE_CODE_CLIENT_CERT`, `CLAUDE_CODE_CLIENT_KEY`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `NODE_EXTRA_CA_CERTS`, `GOOGLE_APPLICATION_CREDENTIALS`, `CLAUDE_CLIENT_PRESENCE_FILE` (Claude Code 2.1.181+; marker file claude reads for Remote Control mobile-push suppression — read-only bind), `OTEL_EXPORTER_OTLP_CLIENT_KEY` / `OTEL_EXPORTER_OTLP_CLIENT_CERTIFICATE` / `OTEL_EXPORTER_OTLP_CERTIFICATE` and the per-signal `OTEL_EXPORTER_OTLP_METRICS_CLIENT_KEY` / `_CERTIFICATE` (the **grpc** OTLP mTLS pair plus the collector's CA bundle — the `http/protobuf` path uses `CLAUDE_CODE_CLIENT_CERT`/`_KEY` instead; the two `METRICS_*` variants were passed through for several releases without a bind, so their paths dangled in-sandbox), `CLAUDE_CODE_SHELL` (names the `bash`/`zsh` binary for the Bash tool; a host path like `/opt/homebrew/bin/bash` would dangle under blaude's empty `/opt` — Claude Code falls back to auto-detection on an unusable value, so the bind only avoids silently discarding the user's choice). **`CLAUDE_CODE_DEBUG_LOGS_DIR`** is a *file* path despite its name (the log file, default `~/.claude/debug/<session-id>.txt`); its **parent directory** is bound read-write (via `${VAR%/*}`) so claude can create the not-yet-existing log file — binding the value itself as a directory would silently skip a custom file path. **`CLAUDE_CODE_SHELL_PREFIX`** and **`CLAUDE_CODE_PROCESS_WRAPPER`** (2.1.208) hold an argv *prefix* (`"/opt/corp/launcher --profile claude"`), not a bare path, so only the first whitespace-delimited token — the executable — is ro-bound. `SHELL_PREFIX` wraps every Bash tool call, hook, status-line command, and stdio MCP server startup, so a dangling path breaks all four at once; `PROCESS_WRAPPER` is canonically under `/opt`, which blaude builds as an empty `--dir`, so it dangles exactly like the `/usr/bin` → `/opt` front-end symlinks. Documented usage sets `PROCESS_WRAPPER` in the settings `env` block rather than as a shell export, in which case it never reaches the passthrough loop and the bind is a no-op.

## AppArmor (Ubuntu 24.04+)

Ubuntu 24.04+ blocks bwrap's user namespaces via `apparmor_restrict_unprivileged_userns`. blaude detects this at startup and warns. Fix with `blaude fix-apparmor` (installs minimal AppArmor profile, requires sudo, idempotent).

## WSL2 Support

Auto-detected via `/proc/sys/kernel/osrelease` or `/proc/version`. Cached in `~/.cache/blaude/wsl-$UID` (see the cache-dir note under Non-Obvious Design Decisions).

- **9P filesystem bugs**: WSL2's drvfs has unfixed `ENOENT` bugs after `rename()`/`fstat()` — only affects `/mnt/*` paths. `sync` is called before/after sandbox execution as mitigation.
- **Warning**: Shown once per session when workspace is on `/mnt/*`. Best fix: use native ext4 (`/home/...`).

## Optional Directory Mounts

These directories are mounted only if they exist on the host (not created automatically, unless noted):

| Directory | Access | Purpose |
|-----------|--------|---------|
| `~/.config/` | **overlay** (readable, writes discarded) | User config (uv, fabric, google-chrome, etc.) — see the write-discarding-overlay entry under Non-Obvious Design Decisions. `~/.config/git/` is still re-shadowed on top — `--ro-bind` if it exists, ephemeral `--tmpfs` if not — redundant under the overlay but correct on the no-overlay fallback path. Mirrors the workspace `.gitconfig` guard; Claude Code 2.1.160 prompts on these writes but `--dangerously-skip-permissions` bypasses that. Both skipped under `--allow-protected-writes`. |
| `~/.agents/` | read-only | Canonical store for `npx skills` (vercel-labs `skills`); global-scope `~/.claude/skills/<name>` symlinks point here. Read-only so the sandbox can't rewrite the shared cross-agent skill store. Project-scope skills already work via the workspace mount. |
| `~/.bun/` | read-only | Bun runtime (`~/.bun/bin` added to PATH); `~/.bun/install/cache` is overlaid (readable, writes discarded) — it was a blank `--tmpfs` before, which hid the host cache and made bun re-download every session. Falls back to that tmpfs, not a bind, when overlays are unavailable |
| `$FNM_DIR` (default `~/.local/share/fnm`) | read-only | [fnm](https://github.com/Schniz/fnm) Node installs; active `node-versions/<v>/installation/bin` resolved onto PATH (see design-decisions note). `FNM_DIR` set in-sandbox. |
| `$PNPM_HOME` (default `~/.local/share/pnpm`) | read-only | pnpm CLI + `pnpm add -g` globals/store; `$PNPM_HOME/bin` added to PATH, `PNPM_HOME` set in-sandbox. Tool-agnostic (also helps nvm/bun). |
| `$COREPACK_HOME` (default `~/.cache/node/corepack`) | read-only | corepack-cached pnpm/yarn binaries (shims live in node's bin); `COREPACK_HOME` set in-sandbox. |
| `~/.yarn/` | read-only | yarn classic global bins (`~/.yarn/bin` added to PATH); yarn globals live in the rw `~/.config/yarn`. |
| `~/arxiv-storage/` | read-write | Research paper management |
| `~/.claude-mem/` | read-write | Persistent memory across sessions (auto-created if claude-mem plugin detected) |
| `~/.notebooklm-mcp/` | read-write | notebooklm-mcp auth (created if missing) |
